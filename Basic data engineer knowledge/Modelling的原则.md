# 🌟 先回答核心问题

> **设计多少个表、每一行代表什么意义？是否有原则？**

答案是：

✔ **有非常明确的设计原则**  
✔ **表的数量 = 由业务过程数量 + 业务实体数量 决定**  
✔ **每一行的意义 = 表的粒度（Grain）决定**  
✔ **粒度设计 = 维度建模最重要的步骤，因为它决定事实表能否正确汇总**

下面我详细解释。

---

# ⭐ 一、一个数据模型到底为什么要分表？

因为在建模中必须区分两类数据：

## **1. 事实（Fact）：发生过的业务事件**

例如：

- 一次订单
- 一次订单明细
- 一次支付
- 一次浏览
- 一次库存变更

这些都是“事件”，它们发生在某个时间点，数量可能很大。

👉 **事实 = 行为、交易、事件**

---

## **2. 维度（Dimension）：稳定的业务实体描述**

例如：

- 用户是谁？
- 商品有什么属性？
- 门店在哪里？
- 时间是什么日期？

👉 **维度 = 描述事物的属性，不是事件**

---

📌 **所以表的数量不是凭兴趣决定，而是由：  
→ 业务过程（行为）  
→ 业务实体（对象）  
自然决定的。**

---

# ⭐ 二、最重要的一步：每个表的“粒度”（Grain）

粒度就是：

> **每一行代表什么业务意义？**

这个是建模的灵魂。

例如订单系统：

|表名|粒度（每一行代表什么）|
|---|---|
|dwd_order|一行 = 一笔订单|
|dwd_order_detail|一行 = 一个订单行|
|dwd_payment|一行 = 一次支付|
|dim_user|一行 = 一个用户|
|dim_product|一行 = 一个商品|

如果粒度不对：

- 会出现重复计算
- 会出现度量指标无法对齐
- 会出现维度无法 join
- 会导致星型模型无法使用

---

# ⭐ 三、那到底如何区分表？遵循哪些原则？

下面是专业数据架构师都使用的 **6 大原则**。

---

# ✔ **原则 1：每个“业务过程”必须有自己的事实表**

业务过程（Business Process）举例：

- 下订单
- 下单明细
- 支付
- 发货
- 退款
- 库存调整
- 浏览
- 加购物车

**一个过程 = 一张事实表**  
**一张事实表 = 一行代表一次事件**

这是 Kimball 维度建模的核心原则。

---

# ✔ **原则 2：每个“业务实体”必须有自己的维度表**

业务实体（Business Entity）举例：

- 用户
- 商品
- 门店
- 日期
- 地理区域
- 商品分类

这些不是事件，而是实体，因此应该有独立维度表。

---

# ✔ **原则 3：一个表只能有一个粒度（one row = one meaning）**

经典错误例子：  
把一个订单表设计成既保存订单头，又保存订单行的信息：

- 订单号
- 用户
- 商品
- 数量
- 订单总金额

这样的话：

- 订单级字段会重复
- 汇总失真

正确方式：

|表|粒度|
|---|---|
|dwd_order_header|一行 = 一笔订单|
|dwd_order_detail|一行 = 一个订单商品行|

---

# ✔ **原则 4：字段要放到与其粒度一致的表（非常关键）**

例如：

- 商品名称：属于商品 → dim_product
- 商品单价：属于订单行 → dwd_order_detail
- 用户生日：属于用户 → dim_user
- 订单金额：属于订单头 → dwd_order_header

👉 粒度不一致，就不能放在同一个表。

---

# ✔ **原则 5：固化的属性放维度，变化的行为放事实**

例如：

- 用户名字（比较稳定） → 维度
- 商品类目（可能变化） → SCD维度
- 订单状态（随事件变化） → 事实表
- 商品价格随时间变化 → SCD2维度或事实表属性

---

# ✔ **原则 6：所有表必须可 join（Star Schema 连通性）**

事实表必须：

- 外键指向维度表
- 能够与维度自由结合做分析

如果某个字段不适合作为维度键，那代表模型设计有问题。

---

# ⭐ 四、总结：你问的东西其实就是 Transform 建模的核心内容

✔ 表的数量 = 由业务过程 + 业务实体决定  
✔ 每一行代表什么 = 表的粒度  
✔ 粒度是设计的第一优先级  
✔ 字段按粒度分配到不同的表  
✔ 事件 → 事实  
✔ 属性 → 维度  
✔ 稳定字段 → 放维度  
✔ 行为字段 → 放事实  
✔ 所有事实表都要能与维度关联

# 🔥 如果不遵循这些原则，会怎么样？

这也是非常关键的问题。

如果模型不遵循 Kimball/Warehouse 标准，会带来一堆严重问题：

---

# ❌ 1. 指标计算会重复、错误

比如：

- 订单表中混入订单行字段
- 用户维度属性放入事实表
- 导致订单金额 × 行数重复累加
- 最终 GMV、订单数全部算错

**不遵循粒度原则 = 指标必错。**

---

# ❌ 2. 模型无法扩展，新增字段要不断改表

因为：

- 粒度不对
- 字段归属不清晰

未来每增加一个业务需求，就要改 10+ 张表，风险巨大。

数据仓库会变丑、变乱、变成“史诗级大坑”。

---

# ❌ 3. join 不清晰，查询慢、数据混乱

如果事实表设计不规范：

- 与维度表 join 行为不明确
- 经常会出现重复行
- SQL 查询变得复杂且易错
- 效能差，甚至拖垮分析系统

---

# ❌ 4. 数据含义模糊，报表团队根本无法保障数据质量

如果每张表没有明确粒度，分析师无法回答：

- 这一行到底代表什么？
- 指标是按订单还是订单行算？
- 订单状态是什么口径？

**数据可信度会崩塌，业务不再信任数据团队。**

---

# ❌ 5. 无法构建星型模型（Star Schema）

星型模型依赖：

- 明确粒度
- 事实与维度分离
- 字段正确归属

如果不遵守这些原则，星型模型根本无法成立。

---

# ❌ 6. 整个数据仓库会变成“宽表垃圾场”

如果没有：

- 粒度定义
- 维度拆分原则
- 字段归属规范

模型会变成：

- 超大宽表
- 字段重复
- 逻辑冲突
- 无法维护

最终只能重建（重花几百万）。
